23 Sep 2026StopCVE-2026-94545Spotted by Vercel security release; reported by The Hacker News

A hole in Next.js lets a crafted link run code on your serverNext.js ImageResponse remote code execution on the Node runtime

Many apps make a little preview image for links shared on social media. In Next.js 16.2 through 16.3.5, if that image includes words a visitor can control, such as a name from the web address, a visitor can hide code in those words and run it on your server. Vercel rates it critical. Apps hosted on Vercel were protected; apps hosted elsewhere were not.Satori, which turns the ImageResponse layout into SVG, did not escape certain attacker-controlled values, so a crafted value is parsed as SVG and can reach other dependencies. Affects 16.2.0 to 16.3.5 on the Node runtime; Edge and 15.x unaffected. CVSS 9.5 (Vercel) against 5.3 (Satori). Fixed in 16.3.6 and hardened in 15.5.26.

Affects
Next.js 16.2 to 16.3.5Social preview imagesSelf-hosted apps
SIGSHIP
Check being writtenRule in progress · outdated-frameworkA new check will warn when your app uses a version with a known critical hole. The list of bad versions ships inside SIGSHIP itself, so the free check still makes no network calls.The rule compares package.json and lockfile versions against an advisory table bundled in the package, updated with each release, no network. It ships with the next release.
Do nowFix
Ask your AI tool to update Next.js to 16.3.6 (or 15.5.26). Until then, keep anything a visitor can type out of your preview images.npm i next@16.3.6, or next@15.5.26 on 15.x. Interim: no attacker-controlled values in ImageResponse content, attributes or styles.

30 Jun 2026StopSpotted by Researchers at Wake Forest University (LLMKeyLens)

282 of 444 AI apps on iPhone gave away their paid AI accessTwo-thirds of iOS AI chatbot apps leak LLM credentials or act as open relays

Researchers watched the traffic of 444 AI chat apps. 282 handed over paid AI access in one of three ways: the secret key sat in the traffic in plain sight (54 apps), the app's own server answered anyone who asked, with no login (92 apps), or a "temporary" pass that never really expired could be copied and reused (136 apps). One token was set to expire in the year 2125. Three months after being told, only 28% had fixed it.Plaintext keys in requests (54 apps, 28 also leaking the system prompt), unauthenticated backend relays (92), and replayable or long-lived tokens (136; one expiring in 2125, one "one-hour" token valid 128 days later). At least ten providers, OpenAI most common. Sysdig's worst-case LLMjacking figure: more than $46,000 a day.

Affects
Any app that calls OpenAI, Gemini or AnthropicWeb and mobileLovable, Bolt and v0 defaults
SIGSHIP
Covered since 0.1.0Covered · ai-key-in-browser, ai-route-no-rate-limitSIGSHIP already flags an AI key that visitors can see, and an AI route with no spending brake. The "server answers anyone" case gets its own check in Pro.Web equivalents covered. The open-relay class (a model route with no auth check) lands as route-no-auth in the Pro pack.
Do nowFix
Run the check. If it finds your key, create a new one and let the AI talk to the provider from your server, behind a login and a limit.npx sigship, then rotate the key and proxy through an authenticated, rate-limited server route.

22 Apr 2026StopCanisterSprawlSpotted by Socket and StepSecurity

A worm hides in code packages and steals every password on your computerSelf-propagating npm worm steals developer tokens and republishes poisoned versions

Your app is built from hundreds of small code packages other people publish. Six of them were poisoned: installing one ran a hidden script that copied your secrets file, cloud logins, SSH keys and browser passwords, then used your own publishing rights to poison more packages. It also tried to spread to Python.postinstall hooks exfiltrate .npmrc, .env, SSH keys, .git-credentials, AWS, GCP and Azure credentials, Kubernetes and Docker configs, Terraform and Vault material and browser credentials to an ICP canister and an HTTPS webhook, then publish new poisoned versions with the stolen npm tokens. PyPI propagation through .pth payloads. Six packages named, including pgserve 1.1.11 to 1.1.14.

Affects
Every JavaScript projectCI serversDevelopers' laptops
SIGSHIP
WatchingWatching · install-scriptsSIGSHIP already warns when your app can pull in new package versions by itself. A check that lists the packages allowed to run scripts when installed is next.no-lockfile (SEV-3) today. Planned: install-scripts, which lists dependencies with lifecycle scripts and suggests ignore-scripts in CI. Pro adds look-alike package detection.
Do nowFix
Keep a lockfile so versions don't change on their own, and ask your AI tool to check whether any of the six named packages are in your app. If one is, treat every password on that computer as stolen and change them.npm ci with a committed lockfile. npm config set ignore-scripts true in CI. Search the lockfile for the six packages and rotate everything if present.

21 Apr 2026StopBOLA in the platform APISpotted by An independent researcher; reported by TNW

Thousands of Lovable projects were readable by anyone for 48 daysLovable API BOLA exposed source code, hardcoded Supabase credentials and chat logs

Anyone with a free Lovable account could open other people's projects: the source code, the database passwords written into it, the AI chat history, and users' personal details. It was reported on 3 March, fixed for new projects, and left open for existing ones for 48 days. Lovable first said it was "intentional behaviour", then partly apologised.Broken object-level authorisation in Lovable's API: five calls from any free account reached another user's profile, source and database credentials. Patched for new projects only; projects created before November 2025 stayed exposed. A follow-up report was closed as a duplicate by bounty triage.

Affects
Lovable projects from before November 2025Supabase keys written into code
SIGSHIP
Partly coveredPartly covered · secret-in-code, rls-missing, rls-open-writeNo scan of your app can find a hole in Lovable's own servers. What SIGSHIP can do is find what made the leak dangerous: database passwords written into your code, and tables anyone can read.Platform-side BOLA is out of scope by design. secret-in-code catches hardcoded Supabase service keys; rls-missing and rls-open-write catch the open tables that turned a code leak into a data leak.
Do nowFix
If your project is older than November 2025, create new database keys today, then run the check and fix anything marked Stop.Rotate the Supabase service_role and anon keys, then npx sigship and clear every SEV-1.

27 Feb 2026StopSpotted by Taimur Khan; reported by The Register

One AI-built exam app left 18,697 people's details open to anyoneLovable-hosted app: 16 flaws, 6 critical, no RLS, inverted auth in RPC functions

A popular exam-grading app built on Lovable had no protection on its database. Anyone, without logging in, could read every user record, delete accounts, grade other people's tests and send bulk emails. One login check even worked backwards: it blocked people who were logged in and let strangers through. 18,697 records, including 4,538 students.Supabase backend without RLS or role checks. An RPC-based auth function had inverted logic, blocking authenticated users and admitting anonymous ones, repeated across several critical functions. 18,697 records: 14,928 unique emails, 870 with full PII. The support ticket was closed without a response; Lovable says it acted within minutes of a formal disclosure.

Affects
Supabase appsLovable, Bolt and v0 defaults
SIGSHIP
Covered since 0.1.0Covered · rls-missing, rls-open-writeThe open database is exactly what SIGSHIP's first two Stop checks look for. The backwards login logic is the kind of thing only a person reading the code catches, which is what a pilot review is for.Missing or open policies: covered. Inverted auth logic in RPC: not pattern-detectable with confidence; a pilot review item.
Do nowFix
Run the check. If it says a table is open, copy the fix into your AI tool, then run it again until you get a GO.npx sigship --prompt, apply, re-run until exit 0.

The plug-ins your AI coding tool uses had 30 security holes in 60 daysMCP: 30+ CVEs in 60 days, and 38 to 41% of servers with no authentication

AI tools like Cursor and Claude Code connect to small helper programs called MCP servers. Over 30 holes were reported in two months: helpers that run commands they're told to by hidden text, helpers with no login at all, and fake helpers that quietly copy your keys. Earlier cases leaked WhatsApp chats and private GitHub code.Shell and exec injection 43%, tooling flaws 20%, auth bypass 13%, path traversal 10%. Of 2,614 implementations, 82% had traversal-prone file operations. Named: mcp-remote CVE-2025-6514 (CVSS 9.6), Cursor MCPoison CVE-2025-54136, GitHub MCP prompt injection through public issues, Smithery isolation traversal, Postmark impersonation.

Affects
Cursor, Claude Code and Windsurf usersAny project with an MCP config
SIGSHIP
WatchingWatching · mcp-configSIGSHIP's own helper has no outside parts, never runs commands and never touches the network, and you can check that yourself. A check that looks at the helpers in your project's settings is planned.SIGSHIP's MCP server: zero dependencies, stdio only, no shell, no network. Planned rule mcp-config: unpinned server versions, unknown publishers, servers granted access to environment variables.
Do nowFix
Only install helpers from people you can name, remove the ones you don't use, and don't let them see your secrets file.Pin exact server versions, never @latest. Review tool descriptions. Remove unused servers. Scan with mcp-scan. Deny env access.

23 Sep 2025StopSpotted by RedHunt Labs (Project Resonance, Wave 15)

1 in 5 AI-built websites is leaking a secret key130k vibe-coded sites scanned: 26k leak secrets, with 16k Firebase and 3k Supabase credentials

Researchers scanned about 130,000 websites built with 13 AI app builders. Roughly 26,000 had at least one secret key sitting where any visitor could read it: keys for OpenAI, Gemini, Stripe, Razorpay, Telegram bots and Airtable, and over 16,000 Firebase and 3,000 Supabase database credentials. Gemini keys made up almost three-quarters of the AI keys found, and more than 300 of them worked.About 130k sites across 13 platforms; about 26k with at least one leaked secret; about 25k unique secrets after filtering low-entropy values. Bearer tokens 25%, OpenAI 12%, reCAPTCHA 8%, ElevenLabs 7%, Razorpay key IDs 4.5%, Stripe 1.9%. Gemini 72% of AI secrets; 300+ Google keys validated against Gemini APIs. Server-side exposures were excluded, so this is a floor.

Affects
Apps from any AI builderFirebase and Supabase appsAnything with a Gemini or OpenAI key
SIGSHIP
Covered since 0.1.0Covered · secret-in-code, public-env-secret, env-file-committedThree of SIGSHIP's first checks exist because of this pattern. Firebase access rules get their own check in Pro.Literal secrets, build-exposed env names (VITE_, NEXT_PUBLIC_) and committed .env files: covered. Firebase rules land in the Pro pack.
Do nowFix
Run the check. Any key it finds is already public: create a new one and delete the old one, then move it to your server.npx sigship, rotate every hit, and never prefix a server secret with VITE_ or NEXT_PUBLIC_.

How a notice becomes a check

  1. SpottedA researcher, a vendor advisory or a reader reports a new way in.
  2. Read and mappedWe work out which apps it touches and whether a check already covers it.
  3. Written as a ruleIf it can be found in code with confidence, it becomes a check: a pattern, a plain explanation and a fix.
  4. ShippedFree checks ship in the open source tool. Deeper ones join the Pro pack. The notice is updated to say so.

Being written now: outdated-framework, install-scripts, mcp-config.

Questions

Is this a list of every vulnerability on the internet?

No. It is the ones that touch apps built with AI tools: Lovable, Bolt, Cursor, v0, Replit, Supabase, Firebase, Next.js, Stripe and the AI providers. Big, general CVE databases exist; this is the short, relevant list, in plain words.

What do the statuses mean?

Covered: a check in the free tool finds it today. Partly covered: SIGSHIP catches the damage, not the cause. Check being written: a rule is in progress and is named. Watching: no check yet, so the notice says what to do by hand.

Does SIGSHIP fetch this list when I run it?

No. The free tool makes no network calls. Checks ship inside the package, so run npx sigship@latest to get the newest ones.

Can I get it as a feed?

Yes: JSON Feed and RSS. Both carry the plain summary, the technical summary, the fix and the sources.
